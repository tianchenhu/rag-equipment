# 设备维保知识库 RAG · 检索质量评测

一个最小可运行的检索增强问答（RAG）实现，用来回答一个具体问题：

> **切块策略到底怎样影响检索质量？值是拍脑袋定的，还是能测出来的？**

项目重点不在"能不能答对"，而在**把链路拆开、定义指标、做对照实验、给出结论**。

---

## 关于分工，先说清楚

**代码在 AI 辅助下完成。** 我负责的部分是：

- 运行、调试、逐环节观察中间结果
- 设计并执行 chunk size 对照实验（五档）
- 构建 25 条标注测试集与 5 条应拒答问题
- 计算并解读评测指标（Hit@k / MRR）
- 分析失败案例，给出改进方向

这个项目的目的，是学会**怎么衡量一条 RAG 链路好不好**——而不是证明我能从零写出一个 RAG。

---

## 链路

```
22 篇文档（平均 370 字）
  → 滑动窗口切块（300 字 / overlap 50）→ 44 个片段
  → text2vec-base-chinese 句向量（768 维）
  → 余弦相似度 top-k
  → 拼接上下文 + prompt 约束
  → 本地 Qwen2.5-7B 生成
```

语料为**模拟数据**（企业真实工单不可得），但按真实设备知识库的结构构造：工单（历史故障处置）、规程（SOP）、规范（安全流程）三类混排——这正是 RAG 落地时最常见、也最容易翻车的数据形态。

---

## 评测结果

基线配置：`chunk=300 / overlap=50 / top_k=3`，44 块，25 条可答问题。

| 指标 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MRR |
|---|---|---|---|---|---|
| 数值 | 0.880 | 0.960 | 0.960 | 1.000 | 0.927 |

按问题类型拆分（Hit@3）：

| 类型 | 命中率 | 条数 | 说明 |
|---|---|---|---|
| direct | 1.00 | 12 | 问法与文档措辞接近 |
| semantic | 0.88 | 8 | 换了说法，靠语义匹配 |
| multi | 1.00 | 5 | 需要跨文档组合 |

---

## 对照实验：chunk size 的影响

overlap 固定 50，top_k 固定 3，只改 chunk size：

| chunk size | 块数 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|---|
| 150 | 81 | 0.880 | 0.960 | 0.925 |
| 200 | 58 | 0.880 | 0.960 | 0.926 |
| **300** | **44** | 0.880 | **0.960** | **0.927** |
| 400 | 25 | 0.800 | 0.880 | 0.857 |
| 600 | 22 | 0.760 | 0.840 | 0.825 |

### 结论：300 是效率拐点，不是 150

150 / 200 / 300 三档的 Hit@3 **完全相同（0.960）**，但块数从 81 降到 44，**减少 46%**。
也就是说，继续往细切只增加索引体积和计算成本，不带来任何检索收益。

400 以上开始明显下滑：单块混进了过多不相关的内容，而向量是整段语义的"平均方向"，
塞得越杂，方向越模糊，检索就越不准。

**所以最优解不是指标最高的那一档，而是"指标持平、成本最低"的那一档。**

> 注：`eval.py --sweep` 会打印"Hit@3 最优：size=150"。这是按数值取的最大值，
> 但 150/200/300 三档并列，结合块数成本后，工程上的选择是 300。

## 拒答控制

构造 5 条语料外问题（例如"去年设备维修总费用是多少""公司设备采购的审批流程是什么"），
在 prompt 首句硬约束"资料中没有答案时直接回答未提及"，配合文档编号溯源。

结果：**5 / 5 全部正确拒答**，没有用模型的训练记忆编造参数。

对工业场景来说，这一条比命中率更重要——**错答一次参数，代价远大于答不出来。**

## 失败分析

25 条问题中，唯一没有进入 top-3 的一条：

> **Q13（semantic）**「机床干久了尺寸越做越小，停一会儿又正常，是什么毛病？」
> 期望召回 `WO-1057`，实际召回 `WO-1115 / WO-1152 / WO-1042`

原因是表述层级错位：问题描述的是**现象**（尺寸漂移、间歇性），文档描述的是**机理**（主轴热变形、温升补偿）。
两者在句向量空间里距离较远。

这类"现象 → 机理"的跨表述检索是纯向量召回的结构性短板，可行的补法有两种：
查询改写（把现象翻译成术语再检索），或混合检索（BM25 关键词分 + 向量分加权）。

## 局限（主动说明）

**1. 语料太短，0.96 偏乐观。**
平均 370 字/篇，切完每篇只有 2 块，"翻对文档"本来就容易——这也正是为什么 150/200/300
三档指标完全一样。换成几百页的设备手册，指标会明显下降，主要掉在跨章节引用上。
**这个数字不能直接类比生产环境。**

**2. 同一文档的多个块会挤占 top-k。**
单步可视化里可以看到：正确答案排第 1，同一篇的第 2 块排第 4，等于把 top_k 变相降到 2。
解法是按 `doc_id` 去重，同一篇只保留分数最高的块。

**3. 语料是模拟生成的。**
结构真实，内容不是真实工单。因此"文档被切碎后仍需跨段拼接"的复杂度，真实场景只会更高。

## 运行

```bash
pip install -r requirements.txt

python rag.py                        # 建索引：22 篇 → 44 块 → 768 维，存 index.npz
python rag.py ask "空压机排气温度高怎么办"
python eval.py                       # 基线：Hit@1/3/5/10 + MRR + 失败案例
python eval.py --sweep               # chunk size 五档对照实验
python eval.py --refuse              # 拒答测试（需本地 ollama 已运行 qwen2.5:7b）
python walkthrough.py                # 单步可视化，逐步打印每一站的中间结果
```

首次运行会下载 `shibing624/text2vec-base-chinese`（约 400 MB）。
如需离线运行，保持 `rag.py` 中的 `local_files_only=True`，并提前把权重放入缓存目录。
